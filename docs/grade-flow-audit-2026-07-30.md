# CONFIRMED

## 1. [blocker/both] Saving a second term in one session wipes the first term's items/attitude
- file: apps/portal/src/offices/gradebook/GradeSheet.jsx:667 (dim encode-save)
- summary: save() rebuilds each learner's whole subject entry from `st.grades` — the roster snapshot fetched once at mount (setRoster is only called in the mount effect, line 383, and never refreshed after a save). Only the CURRENT period's raw/items/attitude are taken from live state; every other period is copied from that stale snapshot. So the second term saved in a session re-writes the entry with the mount-time (usually empty) items/attitude for the term saved earlier, destroying it — while entry[pk] (the grade number) is still recomputed from live memory, so the loss is invisible on screen.
- repro: 1. Teacher opens a fresh sheet (server has nothing for this subject yet, so existing = {}). 2. On the Term 1 tab: set HPS, encode scores + attitude for all 40 learners, press "Save Term 1" — items.q1 / attitude.q1 / raw.q1 land in reg_students_data.grades. 3. Click the Term 2 tab (same page, no reload), encode Term 2, press "Save Term 2". 4. The entry sent contains items = { q2: … } and attitude = { q2: … } only, because `existing` is still the mount-time snapshot where q1 was empty. 5. reg_students_data.grades now has entry.q1 = 87 (recomputed number) but NO items.q1, NO raw.q1, NO attitude.q1. 6. Reload the sheet (or let the checker open it): Term 1 shows every score cell and the attitude column blank, Initial Grade "—", and the adviser's Attitude page shows "—" — an afternoon of Term 1 encoding is gone, with a Term 1 grade number that nothing on the sheet can justify. PENDING-STATE VARIANT: if step 2 was followed by "Submit for checking" (q1 -> for_rechecking), the extended lock loop in setup-submit-is-final.sql PART 2 sees items.q1 changing and step 3's save is REJECTED outright — "Term q1 of X has been submitted and can no longer be edited" — and every further save fails until the page is reloaded, with no hint in the UI that a reload is the fix.
- fix: After a successful save, re-fetch the roster (or splice the just-sent entry into the local roster copy) so `existing` tracks the server. Better: send only the current period (a patch RPC), or build raw/items/attitude for ALL periods from live state instead of mixing live grades with a snapshot's items.
